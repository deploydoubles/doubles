Deployed is not the same as working.

An open standard and a set of reference apps for answering one question: did this deploy actually work?

01Whysuccess is not a status code

A platform can report a deploy as successful while the app behind it is broken: the new release never took over, the queue worker is still running last week's code, the cache silently fell back to the filesystem, the scheduler never started. Deploy Doubles makes those failures visible, from the inside and from the outside, as one exit code.

02Three stepspick, deploy, verify

  1. Pick a double

    Choose the one that matches what you want to test, and read its double.json to see the services, processes and environment it needs.

    npx deploydoubles list --needs postgres,worker

  2. Deploy it

    On any platform, the way you would deploy your own app.

  3. Verify it

    Exit 0 means every check passed on the release you deployed. Anything else comes with a hint for each failing check.

    npx deploydoubles verify https://your-deploy.example --commit 4f2a9c1
Verifying https://your-deploy.example for 4f2a9c1

  ok    release
  ok    database
  FAIL  queue.release
        The worker that processed the probe runs a different release.
        Restart the queue workers after each release so they load the new code.

Vera: Deployed is not the same as working. Failed: queue.release.

03Dub and VeraDub takes the hit. Vera writes it down.

Dub is the double: it stands in for your app and takes the falls. Vera is the verifier: watching from the outside, stopwatch and clipboard in hand.
